# Security

## Trust boundary

MCP Contract Guard reads local JSON files and writes reports. It does not start MCP servers, invoke tools, authenticate to services, or fetch schemas from the network. It is a contract-review aid, not a sandbox or security scanner.

Installation is a separate operation and may download dependencies. Follow your normal package provenance, pinning, and vulnerability-management practices.

## Safe use in CI

- Use synthetic fixtures. Do not commit access tokens, credentials, personal records, private content, or production request/response dumps.
- Reports omit raw argument, result, and schema values, but labels and paths can still disclose data. Tool names, property names, fixture IDs, and filenames must be reviewed before sharing reports.
- Treat snapshots and fixture files as untrusted input. Complex regular expressions, deeply nested schemas, huge instances, and recursive references can consume excessive CPU or memory. Apply CI job timeouts and resource limits. Do not assume the validator is safe for arbitrary hostile submissions.
- External schema references are rejected. Do not add network retrieval or filesystem reference loading as a convenience workaround.
- Run untrusted pull-request jobs with read-only permissions and without secrets. Do not execute a contributor's changed package with privileged credentials simply because the package describes itself as offline.
- Write reports only to intended artifact paths. An explicitly supplied output path is a file-write destination, not a safe filename generated by the tool.
- Review dependency updates and pin the revision used for release gates. A successful contract check does not establish supply-chain safety.

Annotations such as read-only or destructive hints are metadata, not authorization or security guarantees. Contract compatibility cannot certify a tool's behavior.

## Reporting a vulnerability

Use the repository's **Security → Report a vulnerability** option if private vulnerability reporting is enabled. If it is unavailable, open a minimal public issue asking the maintainer for a private reporting channel. Do not include exploit details, secrets, private fixtures, or personally identifying information in that initial issue.

A useful private report includes the affected revision, Python version, a small synthetic reproduction, the impact, and the expected boundary. Please keep the reproduction offline and omit credentials. This project does not promise a response time or a bug bounty.

Only the latest repository revision is currently targeted for fixes; there is no long-term-support promise for older releases.
